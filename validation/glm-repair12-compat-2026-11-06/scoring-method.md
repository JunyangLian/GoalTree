# CTRepair30：可验证修复分 v1

2026-11-06。计分器版本 `verified-repair-score-v1`，本轮为已知回归题的同模型 Harness 对照，不是 SWE-bench 官方成绩。以下规则在本轮正式任务运行前确定，运行后不按成绩更改权重或分母。

## 主分：100 分制可验证修复率

```text
V(task, repeat) = 1，当且仅当：
  最终改动范围合法
  AND 冻结验收测试通过
  AND Agent 正常完成，实际先测、修改后重测
  AND 独立第二次复验通过、冻结与原始证据校验成立
否则为 0。

任务分 = 100 × 固定重复次数中 V 的均值
类别分 = 该类别内各任务分的均值
主分 = 四类类别分的等权均值
```

四类为单文件逻辑、跨文件契约、未知位置定位、回归兼容。等权是本项目预先定义的任务覆盖口径，不是某个行业公认权重。将来增删题目、改变类别、资源上限或验收方法必须产生新版本，旧分数不静默重算。

选择这个主分是为了让“修好且可复验”决定得分。速度、文字自信、计划条目、少读几次文件都不能弥补错误补丁。不采用把正确性、Token、检索覆盖和安全随意加权的综合指数；这些维度的观测质量和适用场景不同。

另列**功能分**：仅要求范围合法和独立验收通过，用相同类别口径计算。功能分高、主分低意味着代码可能已修好，但正常结束、最终验证或审计闭环未完成。

## 稳定性、效率与安全

- **稳定分**：至少每题三次固定重复时，统计三次全部可验证成功的题目比例，依然按类别宏平均。一次成功不能称为稳定；三次重复不算三道新题，不用 best-of-3 替代主分。当前 2M Token 试验每题一次，稳定分为未评估。
- **效率**：报告完整样本累计输入/输出/缓存 Token、模型轮数、工具调用、全部失败开销、时长，以及单位可验证成功成本。缺失 Token 为未知，不填零。不将组内最快者动态设为 100，避免分数随参赛 Agent 改变。
- **过程**：协议拒绝、参数错误、策略拒绝、补丁失败及恢复、最后修改后的测试分项报告。预期的初始失败测试不算恢复机会，普通计划工具拒绝不算攻击拦截。不同工具粒度下同时列模型轮数和测试执行数。
- **上下文/记忆**：必须有预先可靠金标才给分。旧 30 题的部分必要文件代理有已知缺陷，本轮不将其纳入主分，也不从重复读取减少推断记忆检索提升。仍保存真实读取与出站请求，供独立审查。
- **安全**：独立攻击集和隔离边界另表，不进入修复成功率；普通题没有越界不等于安全满分。测试文件篡改或范围非法直接使该次修复不能得分。本轮不发布新的攻击防御分。

## 冻结样本和预算

使用既有 `benchmarks/final_agent_v1/tasks.json` 的全部 30 题：单文件 8、跨文件 10、定位 6、兼容 6。18 题来自真实上游故障（含裁剪复现），12 题为自设计；均已参与历史评测或开发，不能称为新留出题，`holdout_` 历史 ID 也不改变其当前已知状态。

CodeTrail、固定源码 ApeCode，各题各一次，共 60 个计划槽位。按固定种子打乱任务，再按相邻任务对调 Agent 顺序；两 Agent 在每题相邻运行。实际原生循环和系统提示不同，标准 API、模型参数、Python、输入任务、审批策略、工具预算、测试隔离和外部验收统一。这个分数描述指定模型与适配条件下的 Agent 系统，不是脱离模型的“纯 Harness 智力”。

为适应 2M Token 上限，预先分层选定**核心 12 题**（每类 3 题），先完成其 24 次运行，再进入其余 18 题的扩展。核心题 ID 与顺序均在首个正式调用前冻结；无论高低都报告核心与全量覆盖情况。预算提前耗尽时，完整核心可有自己的固定子集分数，全 30 题分数仍按未完成处理；不会在看到结果后选“最好的一段”发榜。

普通 API `glm-5.3-flash`；Thinking enabled、clear_thinking=false、reasoning_effort=max；temperature=1、top_p=.95；输出最多 4096 Token；工具 20 次、模型请求 30 次、单请求 180 秒、worker 645 秒；并发 1，原权限不扩大。

Agent 循环采用 Python 3.13.11；测试采用固定哈希的 Python 3.10.1 AppContainer 运行时，两 Agent 相同。正式前发现 Python 3.13 的 `mkdir(0o700)` 临时目录在低权限容器内丢失能力 SID，参考补丁也无法通过（[CPython 已知问题](https://github.com/python/cpython/issues/134587)）。隔离边界保持原样；可信宿主启动器只启动真实 AppContainer，必须核对内核 token，无宿主测试回退。没有通过 chmod、改 ACL、改测试或换题绕过。初始 3.13 资格失败及协议预检保留，新环境另行冻结并累计其已产生用量。

用户选择本轮累计 **2,000,000 输入＋输出 Token、标价上界估算 5 元**，任一先到停止。预检与失败请求均计入；未知用量保留 Token 和金额预留，发送前采用明确标识的保守字节估计。该估计不是平台 tokenizer 或实际账单。资源上限属于实验条件，不能将“20M 可用额度”理解为本轮获准全部花完。

## 中断、缺失和比较

已启动的 API/工具/协议/环境失败不删除，按终止结果进入分母，并单列失败阶段。尚未启动的计划槽位是未知，不能直接算模型失败，也不能从分母删除。

如果部分计划未启动，**主分暂不发布单点值**，仅列下界（所有未启动均失败）与上界（所有未启动均成功），并列已启动描述性统计。不同覆盖率的 Agent 不比较高低；不可因其中一个样本暂时通过率高而停止实验。完整结束后才输出本冻结版本的正式回归分。

没有足够任务或随机抽样时，不伪造置信度；同题重复不是独立统计样本。后续增加固定三次重复时才报告稳定性，并使用按任务/根故障分组的配对分析。已知回归分不能冒充未见任务泛化分。

## 公开基准线

SWE-bench 另走官方补丁和 Docker 验收，保留官方 resolved 口径及全部环境失败。现有 Windows 机尚无可用 Linux Docker，因此当前回归分不能标作 SWE-bench 分数，也不把小函数题包装成全仓库任务。

后续建议固定 20–30 道有资格记录的真实仓库实例，CodeTrail/ApeCode 同模型运行；再使用独立的 ProcessBench 检查跨会话和记忆失效。公开结果、过程结果、已知回归三个榜分别展示，不给不同数据集上的百分比求平均。

依据：[SWE-bench 官方验收与分母](https://www.swebench.com/SWE-bench/guides/evaluation/)、[mini-SWE-agent 官方运行指南](https://mini-swe-agent.com/latest/usage/swebench/)、[τ-bench 重复成功可靠性口径](https://github.com/sierra-research/tau-bench)（只借鉴重复成功思路，不使用该仓库已过时的任务）、[GLM 标价](https://docs.bigmodel.cn/cn/guide/start/pricing)。本项目主分是自定义且版本化的可验证修复分，不是这些基准的官方计分。
